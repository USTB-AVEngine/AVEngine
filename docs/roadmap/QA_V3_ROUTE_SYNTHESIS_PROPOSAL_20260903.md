# 求解器反向设计路线：方案（2026-09-03）

> 状态：**owner 2026-09-03 拍板并已实施**。裁定原话："合成轨迹也算合法，只要严格跟普通的轨迹一样就行"。
> 第 8 节的三个决定按此落地：合成路线是合法轨迹；顺序先库后合成；边距 0.3 m 与速度范围按占位写。
> 实施记录、实测数字与边界在 `QA_V3_PRESCALE_READINESS_IMPLEMENTATION_20260902.md` 第五轮一节；
> 本文其余部分保留提案原文，作为设计依据。与实施的差别只有两处：速度范围没有"题型现值"可沿用，
> 改为参数 `ROUTE_SYNTHESIS_SPEED_MPS_RANGE`（占位 0.6–1.5 m/s）；card6R 的静止角色不是零位移路线，
> 而是照求解器原有约束"窗口内静止、整段仍有位移"的直线（合成器只出直线，暂停由求解器照旧施加）。

## 1. 要解决的问题

现在路线来自事先做好的库，求解器只从池子里抽：Apartment 是导航网格采样出来的 1933 条，
Kujiale 是 Studio 任务产出的 400 条，其中一半静止。抽不到就报"预算耗尽"。这和机位表接进
求解器之前的状态是同一类问题：本该由求解器保证的东西，交给了一个固定的上游产物。

后果在 Kujiale 的 card1 上最明显。第四轮两轮 canary 各 1/18，把两个 2.5 m 距离底线放宽到 2.0 m
也只到 5/36。旁证是 20 万个随机（相机点，移动路线）组合的几何可行率：两个时刻都离相机 ≥ 2.5 m
且锚帧到查询帧方位扫过 > 30° 的，Apartment 15.7%、Kujiale 5.0%。原因是 Kujiale 的路线太短
（锚帧到查询帧 2.27 s 中位只走 1.88 m）、太少（200 条移动路线）。这不是机位表能解决的。

## 2. 目标

求解器按题目需要**当场构造**一条可走的路线，而不是从库里碰运气；库保留做备选，因为库里的路更自然。

## 3. 现有可用的输入

- 每间房的**可走地面**：Apartment 可以从路线库的 144,975 个采样点栅格化（第三轮做过 5 cm 格，
  当时作遮挡代理失败，但作"哪里能站"是可靠的）；Kujiale 有现成的可行格（`line_of_sight_grid`）。
  更好的来源是舞台包里的导航网格导出，如果能拿到就用它。
- 机位净空表：每个相机点哪些朝向净空、任意视线第一个障碍在几米。
- 题型的几何约束：锚帧/查询帧、答案带、锚带、最小角距、距离底线、视场角、速度范围。
- 时间线生成已经接受任意解出来的路线（`transform_to_solved_routes`），音频按逐帧位置渲，不用改。

## 4. 设计

### 4.1 可走地面栅格进场景配置

场景配置新增 `walkable_grid`（与 `line_of_sight_grid` 同一套坐标约定与 schema），记来源
（路线采样 / 导航网格）、格距、向内收缩的安全边距（占位 0.3 m，防止贴着家具走）。缺它时求解器
不合成路线，只用库，并在 manifest 写明。

### 4.2 反向设计（先做错时族 card1F/card1B）

输入：相机点 C（从净空表的净空朝向里抽，现有逻辑）、答案带、分配的锚带、锚帧 t_a 与查询帧 t_q、
速度范围 [v_min, v_max]、距离底线 d_min。

1. 在答案带里抽查询方位 α_q，在锚带里抽锚方位 α_a，要求 |α_q − α_a| > THETA_HALF（30°），否则重抽。
2. 抽查询距离 d_q ∈ [d_min, d_max]，得到查询位置 P_q = C + d_q·(cos, sin)(ψ + α_q)，ψ 是相机朝向。
3. 锚位置 P_a 在射线 ψ + α_a 上，距离 d_a 由步长决定：|P_q − P_a| = v·(t_q − t_a)/15，v 在速度范围里抽；
   解 d_a，要求 d_a ≥ d_min。解不出就换 v 或重抽。
4. 把 P_a→P_q 的直线向两端延长补满 75 帧（前段可以静止 idle，后段继续直走或停下），得到整条路线。
5. 逐帧检查：全部落在可走栅格内且离边缘 ≥ 边距；不与相机点重合；与对照狗路线的最小间距 ≥ 占位值。
6. 对照狗：先从库里挑（现有 `_pick_other_route` 逻辑），挑不到再用同样方法合成一条满足
   "不同答案带、锚帧分离 ≥ MIN_AZIMUTH_SEP"的路线。
7. 通过后返回 `PointPlan`，路线对象标 `provenance = synthesized`，并记录 α_a、α_q、d_a、d_q、v、边距。

即时族题型（card7/9/2/3/5/6/10/15b/4R）更简单：在答案带与距离范围里抽一个点，抽一个行走方向，
铺直线，同样过栅格检查。card6R 的静止角色就是一条零位移路线，不需要库里的静止路线。

### 4.3 顺序与记录

先用库尝试一个小预算（例如 300 次），失败再合成。manifest 分别记库路线与合成路线的候选数、
合成失败的原因（栅格外、边距不足、速度范围解不出）。fact 记路线来源与合成参数。这样既保留自然路线，
又不让配额被库的短板吃掉。

## 5. 验证（阳性对照不过就不上线）

1. 单元测试用合成栅格：合成路线永远不出可走区域；边距生效；速度范围外解不出时如实拒绝。
2. 两房 canary：Kujiale card1 18 格 smoke 从 5/36 起步，目标 ≥ 24/36；Apartment 不退步。
3. 渲染若干条合成路线的候选，跑像素真值，确认狗没有穿家具：时间线的 `spatial_validation` 与
   像素深度比较能看出穿模。
4. 对比合成与库路线候选的方位扫过角、距离分布，确认合成没有把题目做成"只有一种走法"。

## 6. 成本

| 项目 | 估算 |
| --- | ---: |
| 两房可走栅格与场景配置键 | 0.5 天（Apartment 有采样点，Kujiale 有可行格） |
| 合成器与单元测试 | 1.5 天 |
| 接入七个求解器与 manifest/fact | 1 天 |
| 两房 canary 与像素抽检 | 0.5 天 + 少量 GPU |

不需要重渲净空表；不改任何题型约束与占位阈值。

## 7. 边界与风险

- 直线路比录制路线"假"：动作是走路循环，方向随路线定，看起来是一只沿直线走的狗；研究阶段可接受，
  正式题库前要看人类包反馈。
- 栅格来自路线采样时，没走过的地板会被当成不可走，合成空间偏小；导航网格导出能解决。
- 栅格看不见高度：桌子底下算可走会让狗钻桌子。边距与像素抽检是兜底，导航网格更好。

## 8. 需要 owner 决定

1. 合成路线算不算合法轨迹（相对只用录制/导航路线）。
2. 顺序：先库后合成，还是直接合成。
3. 边距 0.3 m、速度范围沿用题型现值，这两个占位是否认可。

## 9. 本方案不声明

不声明 Kujiale 可出 card1；不改 2.5 m 占位；不声明任何题型可放量。
