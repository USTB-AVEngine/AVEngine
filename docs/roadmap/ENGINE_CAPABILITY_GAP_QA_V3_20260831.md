# 引擎能力差距审计:题型 v3 的自动化需求 vs 现有能力(20260831)

> **目的(owner 指令)**:在 pilot 工单动工前,审一遍现在的引擎是否满足
> 全案 v3 全部题目的自动化出题需求。**方法**:把全案与工单的需求逐项
> 对到仓库现有能力上,每个判定带证据路径,当场查证不靠记忆。
> **判定分级**:✅ 已有(证据在案)/ 🔧 需扩展(在现有结构上加配方或
> 参数,写明改动点与量级)/ ❌ 缺失(全新建,工单已列的标注)/
> ⚠ 结构点(涉及政策或硬合同,要 owner 知情拍板)。
> 本文档供 codex 独立复核(复核清单见第五节)。

## 0. 结论速览

**pilot 六题(①⑦⑧⑨⑪⑯)范围内,引擎没有硬缺口**:所需的全部是
"新配方、新工具、参数化扩展",没有一项要动引擎架构。前提是完成工单
阶段一的五个纯新建件(判分器、干扰项生成器、物理分类器、双声道校验器、
人类作答页面)和三个扩展(停走轨迹配方、画外源启用、像素掩码通道接入
批量线)。

**三个要 owner 知情的结构点**(不挡 pilot,但要按拍板执行):
①像素掩码与 npy 退休政策的流程顺序;②75 帧硬合同;③挖矿器的双源槽
假设。详见第三节。

**确认不够、已正确押后的**:多段式采样(⑰跨段记忆)、家具有向包围盒
(老 T10)——都是全新采样/数据形态,不在本轮范围。

## 3. 三个要 owner 知情的结构点

1. **⚠ 像素掩码通道 × npy 退休政策**:`pixel_visibility.py` 要求同
   渲染器同相机的语义掩码(native 线有);批量线现行政策"出完题只留
   mp4"(batch2d 已执行 npy 退休,37GiB)。**顺序兼容方案**:批量渲染
   加掩码输出 → 出题与可见性判定消费 → 判定完成后照旧退休——政策不变,
   只是"出完题"的定义里加入"可见性判定完成"。代价:渲染时多一个掩码
   通道的临时存储(退休前占用),量级与旧 npy 相当。**需要 owner 认可
   这个顺序调整**。
2. **⚠ 75 帧/5 秒硬合同**:`src/avengine/capture/two_human_capture.py`
   等多处断言 "exactly 75 frames"(formal 合同;review 片可任意长)。
   ⑬⑭的"四句+间隔 ≤5 秒"装配规则、⑧的时间带设计都已适配该合同;
   **任何更长片段/多段需求(⑰)= 合同级架构决策**,押后正确,不建议
   为 v3 动它。
3. **⚠ 挖矿器与程序生成器的双源槽假设**:`generate_qa_v2_questions.py`
   的 `ep_to_slot` 按两端点硬写,`design_qa_batch.py` 按 source1/source2
   设计;schema 层无此限制。⑪(画外第四源)⑫(≥4 发声实体)要把
   槽位逻辑泛化为 N 源——**工具层改造(中量级),不是引擎改动**,但
   涉及在产挖矿器,改造须带回归(旧双源批次重跑一致)。

## 4. 总回答:引擎能力够不够?

**够——在 pilot 六题与主表第一梯队范围内**,以"引擎"指渲染/声学/
timeline/程序/像素真值这一层:没有发现任何需要动引擎架构的需求;全部
差距落在**工具层**(挖矿器泛化、采样过滤器、新建判分/探针件)与
**素材层**(第四衣色、四声种、语音转写),这两层的工作量已被 pilot
工单与素材需求单覆盖。三个结构点(掩码顺序、75 帧合同、双源槽)需要
owner 知情,其中只有掩码顺序需要一个明确"可以"。

**不够、且已正确排除在本轮外的**:多段式(⑰)、家具锚(老 T10)、
片长扩展——都押后了,不影响主投稿题表。
