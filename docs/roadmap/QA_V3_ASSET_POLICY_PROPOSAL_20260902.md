# 题型声明资产政策：方案（2026-09-02，只写方案，不实施）

> 状态：提案，等 Codex 只读审核与 owner 拍板后再改生成器。本文不改变任何现有产物，
> 不宣布任何题型可放量。

## 1. 要解决的问题

现在的生成链是"先有资产，再看能做什么题"：两只狗（黑白边牧、黄色比格）写死在批次
生成器里，题型只在这两只狗上求解。owner 2026-09-02 指出方向应该反过来：**题型先声明
它需要什么样的声源资产，生成器再按声明去注册表里选**。理由是不同题型对资产的要求
本来就不同：

- 有的题只有"同类型的不同个体"才成立，比如按外观区分两只狗、问某一只的毛色；
- 有的题任何单个声源都行，比如首叫时间带、距离变化；
- 有的题需要跨物种混合，但声音内容必须与身份脱钩，比如用音响放狗叫来做"声源在哪"。

资产反过来决定题型，会让人和固定声源进来时无处安放；题型声明资产政策，人和音响
就是按政策自然选进来的。

## 2. 声明放在哪里

每个题型的配置（现在是 `qa_v3_prescale_core_profiles_*.json` 里的一个条目）新增一块
`asset_policy`，与本轮已加的 `visual_requirements` 并列。两块都是"题目的属性"：一块说
要看见什么，一块说用什么演。

```json
"asset_policy": {
  "roles": ["target", "other"],
  "family_rule": "same_family_distinct_instances",
  "allowed_families": ["dog", "human"],
  "motion": {"target": "must_move", "other": "any"},
  "voice": {"shared_clip_across_roles": false, "identity_coupled": true},
  "appearance": {"must_be_distinguishable": true, "referring_expression": "coat_color"},
  "body_geometry_source": "asset_registry",
  "status": "proposal_not_implemented"
}
```

字段含义：

| 字段 | 取值 | 意思 |
| --- | --- | --- |
| `roles` | 角色名列表 | 题目里有几个声源角色，对应现在的 target/other 槽位 |
| `family_rule` | `same_family_distinct_instances` / `any_single_source` / `mixed_families_voice_decoupled` | 三种配对政策，见第 3 节 |
| `allowed_families` | 资产族 | 允许从哪些族里选：dog、human、speaker（音响）等 |
| `motion` | 每个角色 `must_move` / `must_be_still` / `any` | 对路线的要求；card6R 需要一个静止角色，card1 需要目标移动 |
| `voice.shared_clip_across_roles` | 布尔 | 两个角色是否共用同一条声音素材（canonical 音频孪生用） |
| `voice.identity_coupled` | 布尔 | 声音是否必须与身份一致（狗叫必须来自狗）；音响解耦时为假 |
| `appearance.must_be_distinguishable` | 布尔 | 外观是否必须能区分（问毛色的题为真） |
| `appearance.referring_expression` | `coat_color` / `top_color` / `species` / `none` | 题面用什么词指代角色 |
| `body_geometry_source` | `asset_registry` | 预测可见性与净空表的目标带要用的身高体长，从资产注册表读，不再用参数占位 |

## 3. 三种配对政策

1. **同族不同个体**（`same_family_distinct_instances`）：两个角色来自同一族的不同实例，
   外观可区分。适用：card1F/1B、card7、card9、card4R、card5R、card6R、card2/3/5/6/10
   ——所有需要"哪一只"的题。首批人的题按 owner 意见：两个改色的人物、同一把嗓音、
   行走动作，与两只狗完全平行。
2. **任意单声源**（`any_single_source`）：题目只关心一个声源何时/在哪叫，另一角色
   只是干扰。适用：card8（首叫时间带）、card15b（事件计数）。
3. **混族但声音与身份脱钩**（`mixed_families_voice_decoupled`）：允许音响播放狗叫，
   题面不许用"狗"指代声源，只能用"声音"。适用：以后的"声音从哪来"类题；本轮不做。

## 4. 生成器怎么用声明

1. 求解前按 `allowed_families` × `family_rule` 从注册表挑出合法的角色组合；挑不出
   就像现在的扩展题型那样报 `resource_unavailable`，不回退到两只狗。
2. `motion` 决定路线池：`must_move` 的角色从移动路线池抽（本轮的静止路线预过滤就是
   它的特例），`must_be_still` 从静止路线抽，`any` 用全库。
3. `body_geometry_source` 让净空表的目标带与预测可见性按实际身高取值：狗 0.5 m、人
   1.7 m、音响按箱体；净空表已经按 0.5/1.0/1.7 三个高度存了摘要，不需要重渲。
4. `voice` 决定音频调度器怎么选素材：同族不同个体默认各用自己的叫声；共用一条素材
   只在 canonical 孪生里打开。
5. fact 记录实际选中的资产、族、政策名与声明版本，manifest 记每个政策下的候选数。

## 5. 与现有东西的关系

- 不改任何题型的几何约束、锚带/答案带分配、Gate A/Gate B 构造。
- 现有 `pair_assets` 写死两只狗的逻辑保留为 `same_family_distinct_instances` 在 dog 族
  下的特例，历史批次可复现。
- `visual_requirements` 与 `asset_policy` 分开：前者说"要看见谁在哪帧"，后者说"谁来演"。
  两者都由题型声明，都写进 fact。

## 6. 一次性成本与顺序

- 注册表要补：每个资产的族、身高体长、可区分外观标签、指代词、允许的动作（走/站）。
  两只狗与两个改色人先补，音响后补。
- 生成器改动集中在 `build_cell_plan` 的 `pair_assets` 与音频调度器的素材选择，估 1 天；
  测试用合成注册表验证三种政策各能选出/选不出。
- 顺序：Codex 审本方案 → owner 拍板字段 → 注册表补齐 → 生成器改动 → 两房 canary
  （狗）→ 首批人的题（两个改色人）。

## 7. 本方案不声明

不声明任何题型可放量；不声明人的题已可生成；不改占位阈值。

## 8. 静止声源不得当"被问的声源"的通用规则（owner 2026-09-03 已定）

原来的说法是"音响不进动与静类题"，点名 card6、card6R、card10 三个。按同一个逻辑数下来实际不止三个：
**凡是答案取决于声源自身位移的题，静止音响的外观都能替代听音**，因为音响不会走路是常识。

所以规则写成一句通用的：

> **一道题的答案只要取决于某个声源自己的位移，这个声源就不能是静止声源（音响、固定件）。**
> 静止声源仍然可以在同一道题里当另一个声源（干扰项），因为答案不问它。

按现在实现的题型清一遍，受这条规则约束的是八个：

| 受约束（答案取决于被问声源的位移） | 不受约束 |
| --- | --- |
| card1F、card1B（叫声前后的方位带） | card2（此刻方位带） |
| card5、card5R（离你变近还是变远） | card3（第一声来自哪侧） |
| card6、card6R、card10（在动还是站着） | card4R（哪只更近） |
| card16（结尾可见状态，取决于走到哪） | card7、card9（毛色） |
| card17（第二段里在哪） | card8（第几秒） |
| | card11（哪只发的声）、card12（什么声音） |
| | card13、card14（说了什么／谁说的） |
| | card15a、card15b（计数） |

**怎么执行**：这条规则按"被问的声源"判定，不按题型名单判定，所以新增题型自动适用，不用回来改名单。
生成器侧的落点是题型声明里的 `answer_depends_on_source_displacement: true`（占位键名），
求解器给这类题分配角色时，把 `entity_class == "rigid_static_object"` 的资产排除在目标角色之外，
对照角色不受限；fact 里记下这次判定。**本节只是规则，键名与实现待出题侧那一摊落地。**

## 9. 声源身份必须逐 actor 唯一（owner 已定的两次落地，2026-09-03 提炼）

第 8 节说的是"被问的声源不能是静止的"。同一天还有两件事各自落地了同一个更一般的道理，
所以把它写在这里，免得下次又分头发现：

1. 音频返工那摊定了：clip 按 actor 绑定，同一段里两只必须用不同的波形，池里凑不出两条就 fail closed
   （实测 150 段 0 次撞、0 次中途换波形）。
2. 人声那摊定了：两个人各用各的说话人与句子，owner 推翻了"共用同一条波形"的建议。

一般化的判据是：

> **凡是答案取决于"哪个声源"的题型，各个声源的波形身份必须逐 actor 唯一。**
> 两个声源播同一条波形时，"是哪一个"这个问题在音频上就没有唯一答案，
> 题目要么无解，要么只能靠画面猜，而那正好取消了这道题要考的跨模态绑定。

它与第 8 节是同一族的判据，一个管**位移**，一个管**身份**：

| 判据 | 管什么 | 违反时会怎样 |
| --- | --- | --- |
| 第 8 节 | 被问声源的**位移** | 静止声源的外观替人回答，不用听 |
| 本节 | 各声源的**波形身份** | 同一条波形让"是哪一个"没有唯一答案 |

两条都按"这道题的答案取决于什么"判定，不按题型名单判定，所以新增题型自动适用。
防捷径的配套措施也一样：配对独立随机化并配平，再用只给音频的探针验证"只听声音答不到高于随机"。

### 9.1 实现落点：所有声源选择必须走同一个选择器（owner 2026-09-03 要求泛化）

上面写的是规则。owner 明确要求把它写成通用的、不只管人声：

> **任何为角色挑选声音素材的实现，都必须调用同一个选择器，不许各自长一套配对逻辑。**

现在那个选择器是 `avengine.assets.sound_pool.BoundRoleClipSource`，由
`ClassClipSource.bind_distinct_roles(roles)` 产出。它的做法**不是"选完再判断、撞了重选"**，
而是先按 `sound_asset_id` 去重、洗牌、取前 N 个——所以结构上撞不了，也没有重试循环空转的风险；
池里不同 clip 少于角色数就直接 fail closed。

**为什么必须是同一个函数**：同一条规则有两份实现，必然会漂——一边修了另一边没修，
而"两只用了同一条波形"这种错在产物里看不出来，只能靠专门去查才发现
（2026-09-03 就是靠一个 200 段的探针才量出旧实现 45% 的集子会撞）。

**现有各条选择路径的合规状态**（2026-09-03 清点，供落地时对照）：

| 路径 | 怎么选 | 合规 |
| --- | --- | --- |
| `event_pool` + `bind_distinct_roles`（`design_qa_v3_scene_batch.py`） | 逐 actor 取互不相同 | ✅ 唯一合规的一条 |
| `dry_canvas_window`（**当前生产模式**） | `params["SOUND_ASSET"]` 一个资产给所有人 | ❌ 实测 canary v4 的 28/28 与 35/35 个 program 里两只狗**同一条素材、同一个素材窗**，全批只出现一个素材 |
| `design_qa_v3_extended_profile.py`（card11/card16） | 取 `sound_assets[0]`，列表第一个 | ❌ |
| 人声（card12/13/14） | 尚无代码 | ⬜ 落地时必须调同一个函数 |
| 三处写死单个资产的老工具 | 常量 | ⬜ 历史路径，不在本规则范围 |

**所以有一条依赖链要记住**：当前生产模式满足不了本节规则，不是因为 bug，而是因为
dry canvas 在设计上就只有一个共享素材。要满足它必须切到 `event_pool`，而那需要先切声库、
建 catalog、把每条 clip 注册进声资产注册表。**在这条链打通之前，card9（哪只先叫）
在音频侧其实不可答**——两只狗声音完全一样时，答案只能靠 onset 时间差，而不是靠听出是哪只。

## 10. 一次出现的性质决定这个声源能承载哪些题型（owner 2026-09-03 已定）

第 8 节管**位移**、第 9 节管**身份**，两者都是"承载了以后不能怎么摆"。
本节管更前面一步：**这个声源到底能不能承载这类题。**

owner 原话：「狗叫（或者其他声源）是可以出现第几声这种问题，但是人声是不行的。」

> **一个声源能承载哪些题型，取决于它的"一次出现"是什么。**
>
> **可数原子**（一声狗叫、一声猫叫、一次门铃、一次编钟）：一次出现自成一体、可数、可互换
> → 支持"第几声／共几声／首叫在何时"（card8、card15b、card3、card6、card7）。
>
> **承载内容的话语**（一句话、一段音乐）：一次出现是一段有内容的话
> → 支持"说了什么／谁说的"（card12、card13、card14），**不支持计数题**。
>
> 反过来也成立：一声狗叫承载不了 card13/14，因为它没有"内容"。

为什么计数题对话语不成立：**「第三句话」不是一个自然的问题。** 同一个人在一集里说三次
就是三个不同句子，数它没有语义；而"第三声狗叫"是有意义的，因为每声吠可以互换。

### 10.1 后果一：切分策略跟这条走，不跟波形形状走

2026-09-03 把 36 个类别按这条重过了一遍，查出三个缺陷（提交 `5d27484`）：

- 旧的词元启发式匹配 `ring`/`bell`/`beep`/`alarm`，于是 `ringtone`、
  `telephone_dialing_dtmf`、`phone_ring`、`alarm_*`、`buzzer`、`busy_signal` 全被切成碎片。
  **铃声是一段旋律、拨号是一串数字，切掉中间跟切掉一句话的中间是同一个错。**
  `telephone` 一个源文件切出 11.8 个事件。
- 单一的 1.5 秒上限在截断真实的单次出现：`doorbell` 三条**全部**落在 1.53–1.56 秒
  （上限加保护带），全库 105 条被截断。
- 单一的 60 毫秒合并间隔粘不住多音铃声：一个 chime 文件碎成 11 段 0.2–0.5 秒。

改成按类族给参数，并且**去掉启发式、改成显式清单，未刻画过的类别一律落到"只去头尾"**——
切错中间不可逆，不切最坏只是事件偏长：

| 类族 | 类别 | 合并间隔 | 时长上限 |
| --- | --- | ---: | ---: |
| **原子** 一次出现是一下短促发声 | `dog_bark`、`cat_meow` | 60 ms | 2 s |
| **成组** 一次出现是几个音、必须整体保留 | `doorbell`、`doorbell_chime`、`ding_dong`、`chime` | 800 ms | 4 s |
| **持续** 一次出现是一段持续的事件 | 其余全部（人声、音乐、机械、水、火、**以及所有报警与电话**） | 只去头尾，永不切开 | — |

重切结果：`dog_bark` 166 条中位 0.32 秒（旧的是 19 个文件、中位 9.25 秒，塞不进 0.3 秒的窗）；
`speech_playback` 613 个源文件 → 613 个事件，**一对一，一个都没被切开**；
`doorbell_chime` 30→11、`chime` 57→28（合并间隔把每次响粘住了）。

### 10.2 后果二：人声集必须用更长的片子（owner 已定 10 秒 / 150 帧）

用切出来的真实句长算的：

```
人声 613 条：中位 3.74 s   p90 5.39 s   最长 14.60 s
狗叫 166 条：中位 0.32 s
```

在 **5.0 秒**片长里放两个角色各发声一次（留 0.3 秒首静 + 0.3 秒间隔），
两次发声总预算 4.4 秒，每次不能超过 2.20 秒：

| | 单独一次能塞进片子 | 能凑成两角色一轮 |
| --- | ---: | ---: |
| 狗叫 | 166/166（100%） | 166/166（**100%**） |
| 人声 | 418/613（68%） | 43/613（**7%**） |

**5 秒装不下一集两个人说话。** 硬塞只能用最短的 7% 的句子，而短句子系统性地更简单、词更少，
会把 card13/14 的内容题偏掉。

而 **card13/14 在结构上必须两个人同集各说一句**：这些演员**没有口型同步**（音频是贴上去的），
一集只有一个人说话时"是谁说的"给不出任何线索。所以这不是取舍，是推导出来的。

需要的片长：

| 要覆盖的句子比例 | 需要片长 |
| ---: | ---: |
| 50%（句长 3.74 s） | ≥ 8.08 s |
| **75%（句长 4.69 s）** | **≥ 9.99 s** |
| 90%（句长 5.39 s） | ≥ 11.38 s |

**owner 已定：人声集 10 秒 / 150 帧，狗集维持 5 秒。** 用建好的 catalog 复核过，
10 秒下 **462/613（75%）** 的句子能凑成两角色一轮，与事前推导一致。

schema 允许两种片长共存：`avengine_m6_audio_program_v1` 里锁死的只有
`sample_rate_hz=16000`、`ticks_per_sample=3`、`ticks_per_frame=3200`、`video_fps=15`，
**`frame_count` 与 `sample_count` 本来就是可变字段**。渲染成本按帧算，
所以只有人声那部分翻倍，狗集一分不多花。

### 10.3 后果三：现有调度器对人声在算术上不适用

`tools/qa/audio_profiles.py` 里那几个调度器（`schedule_forward_anchor`、
`schedule_first_call_bands`、`schedule_event_count` 等）**全都是为"在 5 秒里摆 2–4 个
不到一秒的事件"设计的**。人声的一次出现比整个片子的一半还长，所以它们不是"需要调参"，
是**不适用**。人声需要自己的调度器，配自己的片长。

记这一条是为了防一个具体的误解：**以为把片长从 5 秒改成 10 秒就够了。** 不够——
片长只是让两句话装得进去，怎么摆、怎么保证两个人各说一句且句子不重复、
怎么和视觉的走位配合，都还是空的。
